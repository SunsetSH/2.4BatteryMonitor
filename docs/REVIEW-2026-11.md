## 2. Идейные несоответствия

1. **«Read-only» шире, чем заявлено.** README: «Settings, lighting and modes are never touched». На деле
   26 драйверов вызывают `SetFeature`, `src/drivers/playstation.cpp:26` переключает DualShock 4 в режим полных
   отчётов (это меняет поведение для других программ), `galaxy_buds.cpp` раз в минуту открывает RFCOMM-соединение
   с наушниками. Всё это, скорее всего, безопасно, но формулировка неточна. Предложение: в CONTRIBUTING записать
   точное правило (что разрешено: запросы чтения, переключение формата отчётов, который сбрасывается при
   переподключении; что запрещено), в README заменить «never touched» на «only battery queries; settings,
   lighting and profiles are never written», а в начале каждого драйвера, который пишет не-запрос, комментарий
   почему это безопасно.
2. **Три палитры вместо одной.** Виджет использует цвета Windows (`widget.cpp:402`), окно истории свою
   сине-серую палитру в стиле Tailwind (`battery_history.cpp:200`, фон `RGB(12,17,28)`), значки в трее третью
   (`main.cpp:445`, зелёный `RGB(30,190,90)`, оранжевый до 30%). Обзор системный светлый. Отсюда ощущение
   «выбивающегося» окна. PLAN уже содержит «вынести цвета в общий заголовок»; предлагаю сразу за основу взять
   системную палитру Windows 11 (нейтральные серые фоны, акцент `#0067C0` / `#60CDFF`).
3. **Цвета нарушают правило 3 из DESIGN.md.** Правило: синий значит зарядка. В окне истории подпись
   «Blue: battery level; green: charging»: зелёный там значит зарядку. В трее оранжевый до 30% есть, в виджете
   его нет.
4. **Два порога «мало заряда».** Красный в виджете и трее всегда при 15% (`LOW_BATTERY`), а порог уведомления
   устройство получает свой (5–40%). Пользователь, выставивший 30%, получает уведомление, но цифра остаётся белой.
   README это признаёт, но логичнее, чтобы красный следовал порогу устройства (глобальные 15% остаются по
   умолчанию).
5. **Тема берётся из двух разных настроек.** Виджет и меню следуют `SystemUsesLightTheme` (панель задач), окно
   истории `AppsUseLightTheme`, обзор никакой. При тёмной панели и светлых приложениях меню, открытое из
   светлого обзора, будет тёмным. Правило: окна следуют `AppsUseLightTheme`, всё, что на панели задач,
   `SystemUsesLightTheme`; меню, открытое из окна, следует окну.
6. **Недокументированный API вопреки CLAUDE.md.** `ApplyMenuTheme` (`main.cpp:159`) вызывает `uxtheme.dll`
   по ординалам 135/136 (`SetPreferredAppMode`, `FlushMenuThemes`). Это общепринятый приём, но правило проекта
   требует документированных API. Нужен короткий ADR: зачем, на каких сборках проверено, что будет, если
   ординал исчезнет (сейчас код безопасно ничего не делает).
7. **«15 languages» при неполных переводах.** Из 136 фраз `_template.txt` 12 языков не переводят 75, русский 52,
   польский 27. В окне обзора на русском видно «100%, fully charged», «demo». Варианты: дописать переводы
   (основной путь), а в README писать «15 languages, N fully translated». Добавить в `make check` отчёт о
   покрытии (не падение): сколько фраз не переведено в каждом файле.
8. **`detail` это готовая английская строка.** Драйверы пишут «L 80%, R 75%, case 40%» в `DeviceStatus::detail`:
   её нельзя перевести (драйверы не знают `T()`) и неудобно разбирать из `--json`. Предложение: структурные
   поля `left`, `right`, `case` (−1 если нет), а строку собирает интерфейс. В JSON поля добавляются, `detail`
   остаётся для совместимости. Изменение формата `--json`, требует согласия владельца.
9. **Тесты как правило против факта.** CLAUDE.md: «у каждого драйвера тест». Факт: 29 из 93 (T1). Либо правило
   ослабить до «у каждого нового и изменённого драйвера», либо включить покрытие в план с явным списком.

## 3. Быстродействие

Сейчас: один поток, 90+ драйверов строго по очереди, после опроса результат целиком уходит в интерфейс. На машине
с одним устройством полный проход 370–630 мс, это нормально. Медленно становится, когда устройство спит или
молчит: каждый такой драйвер тратит свой таймаут целиком.

Примеры худшего случая по коду: Rapoo до 5 с на интерфейс (`rapoo.cpp:95`), Areson 2 × (1,8 с + 0,2 с)
(`areson.cpp:34–39`), AirPods до 3 с при первом запуске сканера (`airpods.cpp:236`), GameSir BLE повтор через
1,5 с (`gamesir_ble.cpp:218`), Plantronics и ZOWIE по 1 с на чтение. Два спящих устройства легко дают 5–10 с, и
всё это время «Refresh now» ничего не показывает.

Предложения по убыванию пользы к затратам:

1. **Замер по драйверам.** `--list --timing` (или секция в `--dump`): время каждого `PollX` и число открытых
   коллекций. Без этого остальное делается вслепую. Пара строк в `PollAllDevices`.
2. **Промежуточные результаты.** Отправлять в интерфейс то, что уже найдено, после каждой группы драйверов, а не
   в конце. Окно обзора заполняется сразу, долгие драйверы доезжают позже. Нужен признак «опрос не закончен»,
   чтобы `OnResults` не удалял ещё не опрошенные устройства.
3. **Параллельный опрос по устройствам.** Захват `VID:PID` у драйверов почти всегда статический (таблицы
   VID/PID). Разделить драйвер на две фазы: `Match` (чистая функция по списку коллекций, задаёт порядок и
   захват, как сейчас) и `Query` (ввод-вывод). Фаза `Query` для разных физических устройств идёт параллельно
   в пуле из 4–8 потоков. Время опроса становится равным самому медленному устройству, а не сумме. Это
   меняет архитектуру из ADR 0002, нужен новый ADR; переводить драйверы можно по одному, старые остаются
   последовательными.
4. **Источники вне HID отдельно.** Bluetooth через SetupAPI, BLE-реклама, Phone Link, Windows.Gaming.Input,
   RFCOMM (Galaxy Buds, Nothing) не зависят от HID-цепочки по захвату `VID:PID`, им нужен только итоговый
   список имён / контейнеров. Их можно запускать параллельно с HID-цепочкой и сливать в конце, сохранив
   текущие правила дедупликации.
5. **Пассивные драйверы как слушатели.** Rapoo, Switch Pro и подобные ждут, пока устройство само пришлёт отчёт.
   Вместо ожидания до 5 с на каждом опросе держать дескриптор открытым в фоновом потоке и отдавать последний
   полученный отчёт с меткой времени. Опрос становится мгновенным, данные свежее.
6. **Кэш перечисления HID** (H4): между `WM_DEVICECHANGE` список коллекций не меняется.
7. **Отступ для спящих.** Устройство, которое не ответило N раз подряд, опрашивать реже (×2, ×4, до 10 минут) и
   сразу при `WM_DEVICECHANGE` / выходе из сна. Меньше таймаутов и меньше пробуждений радиоканала.
8. **Адаптивный интервал.** Чаще при зарядке и ниже порога (кривая быстро меняется), реже при стабильном
   уровне. На ноутбуке от батареи интервал ×2 (`GUID_ACDC_POWER_SOURCE`).
9. **Пауза при блокировке и выключенном экране** (`WTSRegisterSessionNotification`,
   `GUID_CONSOLE_DISPLAY_STATE`): никто не смотрит, а каждый опрос будит мышь и гарнитуру.
10. **Виджет без опроса раз в секунду.** `Reconcile` каждую секунду перечисляет панели задач, читает реестр и
    двигает окно. `SetWinEventHook(EVENT_OBJECT_LOCATIONCHANGE)` на `TrayNotifyWnd` плюс редкий
    страховочный таймер (5–10 с) дают тот же результат дешевле. U4 и U5 из раздела 1.

## 4. Совместимость

Главный рычаг не новые протоколы, а проверка существующих: большинство из 100+ семейств помечены «untested».
Поэтому первые два пункта про обратную связь от владельцев.

### 4.1 Процесс

1. **Отчёт в один клик.** В меню устройства и в окне обзора «Report this device...»: собирает `--dump` для этого
   `VID:PID`, модель, версию и открывает в браузере GitHub issue с заполненным шаблоном (ничего не отправляется
   само, пользователь видит текст). Вариант для «устройство не найдено»: тот же отчёт по всем коллекциям.
2. **Шаблоны issue** `.github/ISSUE_TEMPLATE/`: «работает / не работает» с полями из `--dump`, «новое
   устройство» со ссылкой на инструкцию по USB-захвату.
3. **Матрица проверок в `docs/DEVICES.md`**: колонка «проверено владельцем, версия, дата» вместо общего списка.

### 4.2 Linux: ядро уже знает заряд многих устройств

Ядро Linux отдаёт заряд через `/sys/class/power_supply/` для `hid-logitech-hidpp`, `hid-sony`, `hid-nintendo`,
`hid-steam`, `hid-apple`, Wacom и любых HID-устройств с usage Battery Strength. Тот же каталог читает UPower.
Чтение `power_supply` (или UPower по D-Bus) закрывает большую часть фазы 2 из PLAN без единого протокола и без
прав udev. Драйверы проекта тогда нужны в Linux только для того, чего ядро не умеет.

## 5. Интерфейс

### 5.1 Окно обзора

Сейчас: светлое окно с системным ListView в рамке `WS_EX_CLIENTEDGE`, серая плашка статуса, три текстовые колонки,
две кнопки. Выглядит как утилита Windows XP рядом с тёмным виджетом и тёмным окном истории.

Предлагаемый вид, в той же манере, что окно истории (своя отрисовка, без новых зависимостей):

```text
+------------------------------------------------------------+
|  2.4BatteryMonitor                         [обновить] [...] |
|  Все устройства · обновлено 12 с назад                      |
|                                                            |
|  +------------------------------------------------------+  |
|  | [гарн.]  HyperX Cloud III Wireless          47%      |  |
|  |          Приёмник 2,4 ГГц · ~9 ч до разряда  ======-- |  |
|  +------------------------------------------------------+  |
|  | [мышь]   Logitech G PRO X 2           64%  [молния]   |  |
|  |          Приёмник 2,4 ГГц · заряжается      ======--- |  |
|  +------------------------------------------------------+  |
|  | [наушн.] AirPods Pro                  85%            |  |
|  |          Bluetooth · L 85% · R 90% · кейс 40%        |  |
|  +------------------------------------------------------+  |
+------------------------------------------------------------+
```

- Карточка на устройство: значок типа из Segoe Fluent Icons (те же глифы, что в виджете), имя, крупный
  процент, полоса уровня, строка подробностей (подключение, зарядка, сон, прогноз из `runtime_estimate.h`).
- Цвета по общей палитре (раздел 2, п. 2), тёмная и светлая тема по `AppsUseLightTheme`, тёмный заголовок
  через `DWMWA_USE_IMMERSIVE_DARK_MODE` (как уже делает `battery_history.cpp:236`). На Windows 11 22H2+ фон
  Mica через `DWMWA_SYSTEMBACKDROP_TYPE` (документирован), на Windows 10 сплошной фон.
- Клик по карточке открывает историю, правый клик меню этого устройства (то же, что подменю в трее). Сейчас
  до истории два уровня меню.
- Перетаскивание карточек вместо «Move left / Move right» в меню.
- Пустое состояние: вместо «No devices found» короткая подсказка и кнопка «Report a missing device» (4.1).
- Клавиатура: стрелки по карточкам, Enter история, Shift+F10 меню (правило 9 из DESIGN).

Вариант дешевле: оставить ListView, но `NM_CUSTOMDRAW` с цветами палитры, значки типа через ImageList, колонка с
полосой уровня, тёмный заголовок. Это убирает главный визуальный разрыв за малую часть работы, но заголовок
колонок ListView в тёмной теме без недокументированного `DarkMode_Explorer` останется светлым.

### 5.2 Виджет и трей

- Левый клик по виджету сейчас открывает то же контекстное меню, что и правый (`WidgetProc`). Привычнее: левый
  клик открывает компактную панель (flyout) над панелью задач со списком карточек из 5.1, правый меню.
- Одинаковая логика «полностью заряжен» в виджете и трее: сейчас в `ApplyEntry` и `UpdateWidget` она записана
  по-разному (`charging && !full && shown < 100` против `full || charging && percent >= 100`). Вынести в одну
  функцию.
- Красный по порогу устройства (раздел 2, п. 4), оранжевый «скоро» одинаково в виджете и трее.

### 5.3 Настройки

Все настройки живут в контекстном меню на 170 строк кода и несколько уровней вложенности. Отдельное окно
«Settings» в стиле обзора (разделы: Display, Devices, Alerts, History, Updates, Language) решает три проблемы:
меню становится коротким, у настроек появляется место для пояснений, `TaskbarOffset` и `IgnoreDevices` перестают
быть «только через реестр». Меню трея оставить для частых действий: обновить, обзор, история, выход.

### 5.4 Окно истории

- Цвета по общей палитре и правилу «синий значит зарядка» (раздел 2, п. 3).
- `WM_DPICHANGED` (U3).
